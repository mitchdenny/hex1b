# Offline HWT recording spike

From the repository root:

```sh
dotnet run --project samples/HwtRecordingDriver/HwtRecordingDriver.csproj -- --output src/site/public/recordings
```

Use another `--output` directory for local checks. Requires .NET 10 and Hex1b's
native PTY support. The project reference builds `HwtRecordingSample`; a build
target copies its executable, dependencies, and verbatim sources beside the
driver. The driver launches the built DLL with `dotnet`, never a runtime build.
The sample uses a pinned published Hex1b package; the outer recording terminal
still uses this checkout's Hex1b and HWT1 implementation.
Run a normal build again after editing the sample; `--no-build` uses the previous
executable **and its matching copied sources**.

## Output

- `graphics.hwt.json`: `{ "format": "hex1b-hwt-recording", "version": 1,
  "durationMs": ..., "frames": [{ "timeMs": 0, "data": "..." }, ...] }`.
  Each `data` is base64 of a complete, unmodified binary HWT1 frame, including
  image payloads. Times are monotonic milliseconds relative to the first capture;
  duration includes the final human-readable dwell and is at least the last time.
- `sample.json`: sample ID, title, description, sample-directory run command,
  relative recording filename, and the actual C# sources, project, README,
  license and `.gitignore`.
  It does not present driver implementation as sample source.

The site's build then exports those same files as a static Git repository and
adds clone metadata to the manifest. Use `npm run record --prefix src/site` for
the complete recording-and-repository workflow.

**Both this JSON envelope and HWT1 are experimental and same-build-only.** Build
the .NET producer and first-party browser client from the same checkout. This is
not a stable archive format, compatibility promise, or new shipped recording API.
Recordings contain screen content and image bytes; do not record secrets.

## Scenario and checks

The outer `Hex1bTerminal` uses `Hwt1PresentationAdapter`, which advertises KGP and
Sixel support to the ordinary PTY child. An independent reader preserves and
acknowledges every returned frame using its metadata revision. The adapter may
coalesce terminal output before projection; this is a state recording, not a
lossless log of every ANSI write.

Before the first frame read, the driver waits for the child's initial screen and
both graphics to be ready. The first capture is a full baseline containing that
populated gallery at time zero, so paused browser playback opens on useful content.
No returned frames are discarded. The scenario waits for both the real screen and captured HWT state at counts 0, 1,
and 2. Each state must contain both labeled, substantial graphics placements
with complete recorded RGBA resources. Two-second pauses are intentional viewing
time, not readiness checks. The result normally lasts roughly 6–10 seconds.

A driver-local decoder verifies full/delta revision continuity, cell records,
resource retention, complete image payloads, and projection warnings. Capture is
stopped and the recording finalized and saved **before** activating Quit, so
alternate-buffer teardown cannot erase the final playback state.

The driver rejects more than 10,000 frames, 10 minutes, or 64 MiB of serialized
recording JSON. This scenario additionally has a 45-second overall deadline,
12-second milestone bounds, and a 5-second clean-exit bound. Failure cancels and
observes reader, scenario, and process tasks and disposes the owning terminal/PTY.
Non-cancellation failures make the command fail. The inspector deliberately only
supports the RGBA resources generated by this sample, not all possible HWT1 input.

Run the focused driver tests with:

```sh
dotnet test --project samples/HwtRecordingDriver/Tests/HwtRecordingDriver.Tests.csproj
```
